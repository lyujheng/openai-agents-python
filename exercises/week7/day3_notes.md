# Week 7 Day 3-4：Agentic RAG

## 前置问题：RAG 是什么，解决什么问题？

### LLM 的核心缺陷

LLM 的知识有两个硬伤：

1. **知识截止**：训练数据有截止日期。问"2025 年 Python 3.13 有什么新特性？"，如果模型训练数据只到 2024 年初，它答不上来，或者编造。
2. **没有私有数据**：问"我们公司上个季度的销售数据是多少？"——这些数据从来没进过训练集，LLM 根本不知道。

共同点：**LLM 需要的信息不在它的参数里。**

### RAG 的思路

RAG = Retrieval-Augmented Generation，检索增强生成。思路很直接：

```
LLM 不知道的东西 → 先从外部数据源检索出来 → 塞进 prompt 里 → LLM 基于这些信息回答
```

具体例子：

```
用户问："我们 Q3 营收多少？"
    ↓
检索：从公司数据库/文档库里搜到《Q3 财报.pdf》
    ↓
拼接 prompt：
    "参考文档：Q3 营收 2.3 亿，同比增长 15%...
     用户问题：我们 Q3 营收多少？
     请根据参考文档回答。"
    ↓
LLM 回答："根据 Q3 财报，营收 2.3 亿，同比增长 15%。"
```

没有 RAG：LLM 要么说"我不知道"，要么编一个数字。有了 RAG：LLM 基于真实文档回答，有据可依。

### 典型应用场景

| 场景 | 外部数据源 | 为什么 LLM 自己答不了 |
|------|-----------|---------------------|
| 企业知识库问答 | 内部文档、Wiki、Confluence | 私有数据，从未进过训练集 |
| 客服机器人 | 产品手册、FAQ、工单历史 | 产品细节太具体，模型记不住 |
| 法律/医疗咨询 | 法规库、临床指南 | 需要精确引用原文，不能编造 |
| 代码问答 | 项目源码、API 文档 | 你的代码库是私有的 |
| 实时资讯 | 新闻、论坛、最新论文 | 知识截止后的信息 |

一句话总结：**凡是 LLM 训练数据里没有的、但你有的信息，都可以用 RAG 喂给它。**

### RAG vs 微调：深入对比

#### 本质区别

**RAG**：不改模型本身，在推理时临时给它"参考资料"。类比：**开卷考试**——翻书找答案。

```
用户问题 → 检索相关文档 → 文档 + 问题一起塞进 prompt → 模型基于文档回答
```

**微调**：改模型本身的参数，把新知识"烧"进权重里。类比：**闭卷考试**——凭记忆答题。

```
准备训练数据 → 在基座模型上继续训练 → 得到新模型 → 用新模型回答
```

#### 各自擅长什么

| 维度 | RAG | 微调 |
|------|-----|------|
| 擅长 | 注入**事实性知识**（数据、文档、条目） | 改变模型的**行为模式**（风格、格式、推理方式） |
| 更新 | 换文档就行，秒级生效 | 要重新训练，几小时到几天 |
| 成本模式 | 推理时多一步检索，token 用量增加 | 训练一次性成本高，推理时无额外开销 |
| 幻觉控制 | 好——能要求"只用文档内容回答"，答案可追溯 | 差——知识混在参数里，分不清哪些是训练数据哪些是编的 |
| 数据量要求 | 几篇文档就能用 | 通常需要数百到数千条高质量训练样本 |
| 上下文限制 | 受 context window 限制，塞不下太多文档 | 无此限制，知识压缩在参数里 |

#### RAG 搞不定的场景

RAG 不是万能的，以下情况必须用微调：

**1. 需要改变"技能"而非"知识"**

想让模型学会看 X 光片诊断肺炎——塞一堆医学教材进 prompt 也没用，模型缺的不是知识，而是推理能力。想让模型把中文稳定地翻译成公司特有术语体系——RAG 可以提供术语表，但模型未必能严格遵守，微调能把这个行为模式固化。

**2. 知识量太大，检索不过来**

即使 128k token 的模型，塞满也就约 300 页文本。知识库 10 万篇文档，每次只能检索 top-5 塞进去。检索质量成了瓶颈——搜不到就等于没有。微调把知识压缩在参数里，不占 context window。

**3. 高频调用要压成本**

RAG 每次请求都要：检索延迟（50-200ms）+ 多塞 3000-5000 token 的文档。如果每天百万次请求，每次都塞同样的背景知识，微调一次永久生效，推理时零额外成本。

**4. 格式和风格要极致稳定**

想让模型永远用日语敬语回答、输出严格 JSON、遇到不确定就说"需要人工确认"——这些是行为习惯，不是知识。system prompt 里写规则，模型经常"忘记"。微调几百条示例，行为就稳定了。

#### 判断框架

```
需要的信息会变吗？
├─ 经常变 → RAG（换文档就行）
└─ 基本不变 → 继续看 ↓

需要的是知识还是能力？
├─ 知识（事实、数据、文档内容）→ RAG
└─ 能力（推理方式、输出格式、语言风格）→ 微调

调用量大吗？
├─ 每天百万次请求，每次都要塞同样的背景知识 → 微调更省钱
└─ 调用量不大，或者每次需要不同的文档 → RAG
```

一个直觉判断：**你想让模型"知道"什么 → RAG。你想让模型"会做"什么 → 微调。**

#### 实际中经常组合使用

生产环境往往不是二选一：

```
基座模型（GPT-4o / DeepSeek）
    ↓ 微调
领域模型（学会了医学推理方式 + 输出格式）
    ↓ RAG
最终系统（用检索到的患者病历和临床指南回答具体问题）
```

微调解决"怎么思考"，RAG 解决"基于什么信息思考"。大多数"让 LLM 用上我的数据"的需求，RAG 是首选；但微调在行为模式、高频成本、格式稳定性上有不可替代的价值。

## 问题背景：为什么简单 RAG 不够？

理解了 RAG 解决的根本问题之后，下一个问题是：简单 RAG 的固定流程在哪些场景下不够用？

简单 RAG 的流程是固定的管道：

```
用户问题 → 向量检索（一次，top-k） → 拼接上下文 → LLM 生成回答
```

不管什么问题，都是同一套流程。三个场景会暴露问题：

### 场景一：查询-文档词汇不匹配

用户问"Python 怎么做真正的并行？"，文档里写的是"multiprocessing"、"GIL"。简单 RAG 用原始问题去检索，关键词对不上，搜不到。需要**查询重写**——把用户措辞翻译成文档的语言。

### 场景二：需要多篇文档综合

用户问"对比 Python asyncio 和 Rust async/await 的异同"。一次检索 top-3，可能只搜到 Python 相关的，漏掉 Rust。需要**多轮检索**——分别搜两个概念，确保两边都有。

### 场景三：检索深度不够

第一次搜只拿到摘要，信息不足以回答。简单 RAG 没有"信息够不够"的判断机制。需要**自适应深度**——评估结果，不够就读全文、换关键词、继续搜。

### 本质区别

| | Simple RAG | Agentic RAG |
|---|---|---|
| 检索策略 | 固定：一次检索 top-k | 动态：agent 自主决定 |
| 查询 | 直接用用户原文 | 可以分解、重写、细化 |
| 轮次 | 固定 1 轮 | 自适应，信息够了才停 |
| 判断力 | 无——拿到什么用什么 | 有——评估结果是否充分 |
| 成本 | 可预测（1 次检索 + 1 次 LLM） | 不可预测，但质量通常更好 |

Simple RAG 像自动售货机——按一个按钮出一个结果。Agentic RAG 像真人研究员——先想想要搜什么，搜完评估够不够，不够就换个角度再搜。

## 技术原理

### 核心架构

```
                    ┌─────────────────────────────┐
  用户问题 ────────→│       RAG Agent              │
                    │  检索工具箱：                 │
                    │  - semantic_search（语义搜索）│
                    │  - keyword_search（关键词）   │
                    │  - read_document（读全文）    │
                    │  - list_all_topics（浏览目录）│
                    │                               │
                    │  自主决策循环：                │
                    │  分析问题 → 选工具 → 检索     │
                    │  → 评估结果 → 够了就回答      │
                    │           → 不够就继续搜      │
                    └─────────────────────────────┘
```

这其实就是 ReAct 模式用在检索场景——Agent 的"行动"是调用检索工具，"观察"是看检索结果够不够。

和简单 RAG 的关键区别：**简单 RAG 是 Python 代码控制检索流程，Agentic RAG 是 LLM 控制检索流程。**

### 5 种高级 RAG 模式

| 模式 | 描述 | 实现方式 |
|------|------|---------|
| 自适应检索 | 根据问题复杂度决定检索深度 | 简单问题搜一次就回答，复杂问题多轮 |
| 查询分解 | 把复杂问题拆成多个子查询 | 比较类问题 → 分别搜两个概念 |
| 查询重写 | 检索结果不好时换关键词 | semantic_search 没结果 → 试 keyword_search |
| 多源聚合 | 从多个数据源检索并合并 | 多个检索工具，各有侧重 |
| 验证回路 | 检查回答是否有文档支持 | 要求 agent "必须基于检索到的文档" |

练习代码不是分别实现这 5 种模式，而是通过一个 Agent + 多个工具 + 好的 instructions 把它们融合在一起。Agent 自己会根据情况使用不同的模式。

### 实现架构

#### 简单 RAG（baseline）

```python
# 固定流程，纯 Python 控制。
docs = retrieve(question, top_k=3)           # 一次检索
context = "\n".join(doc.content for doc in docs)  # 拼接
answer = llm(f"参考文档：{context}\n问题：{question}")  # 生成
```

Agent 只在最后一步（生成回答）出场。检索策略完全由代码决定。

#### Agentic RAG

```python
rag_agent = Agent(
    name="Agentic RAG",
    instructions="你是智能研究助手...",  # 检索策略指引
    tools=[
        semantic_search,   # 语义检索——适合自然语言查询
        keyword_search,    # 关键词检索——适合精确概念
        read_document,     # 读全文——看到摘要不够时用
        list_all_topics,   # 浏览目录——不确定搜什么时先看看有什么
    ],
)
result = await Runner.run(rag_agent, question)
```

Agent 全程控制。它自己决定：
- 先用哪个工具搜
- 搜到的结果够不够
- 要不要换关键词再搜
- 要不要读某篇文档的全文
- 什么时候信息充分了可以回答

### 4 个工具的设计思路

```
    semantic_search("Python 并发编程")
         ↓
    返回 top-3 文档的标题 + 摘要预览
         ↓
    Agent 判断："摘要不够详细，需要读 doc_002 的全文"
         ↓
    read_document("doc_002")
         ↓
    返回完整内容
         ↓
    Agent 判断："还缺 Rust 方面的信息"
         ↓
    keyword_search("rust concurrency")
         ↓
    ...
```

工具分层设计：
- **粗检索**（semantic_search, keyword_search）：先快速定位相关文档
- **细检索**（read_document）：对感兴趣的文档读全文
- **探索**（list_all_topics）：不知道搜什么时先看看知识库有什么

这个分层让 Agent 能用低成本操作（粗检索）快速定位，再用高成本操作（读全文）深入。

## 生产环境的 Agentic RAG

### 选型决策

```
你的检索场景是什么样的？
│
├─ 用户问题直接对应一篇文档？
│   └─ YES → Simple RAG 就够了
│       （FAQ、产品说明查询、单一知识点）
│
├─ 可能需要多篇文档综合？
│   └─ YES → Agentic RAG
│       （比较类问题、跨领域问题、深度分析）
│
├─ 检索延迟敏感（要求 <2s 响应）？
│   └─ YES → Simple RAG + 查询改写
│       （不用 Agent 循环，但加一步 LLM 改写查询）
│
└─ 对回答质量要求极高？
    └─ YES → Agentic RAG + Reflexion
        （检索+回答+自评+重来）
```

### 真实系统的检索工具

练习中用 dict 模拟，生产环境换成：

| 练习中 | 生产环境 |
|--------|---------|
| `retrieve(query)` 关键词匹配 | ChromaDB / FAISS / Pinecone 向量检索 |
| `_keyword_match_score()` | BM25 / Elasticsearch 全文检索 |
| `DOCUMENTS` 字典 | 向量数据库 + 文档存储 |
| `read_document(doc_id)` | S3 / 数据库读取原始文档 |

但架构思路完全一样：Agent + 多个检索工具 + 好的 instructions。

### 成本控制

Agentic RAG 的最大风险是成本不可控——Agent 可能无限循环检索。控制手段：

- `max_turns` 限制 Agent 循环次数
- 工具缓存：相同查询只执行一次（Day 5 会详细讲）
- 检索结果截断：返回摘要而非全文，减少 context 长度
- 早停：instructions 中写"如果前两次检索已经覆盖了问题的主要方面，就可以回答"

## 代码实现要点

练习代码位置：`exercises/week7/day3_agentic_rag.py`

### 对比实验设计

同一组问题分别跑 Simple RAG 和 Agentic RAG：

| 问题类型 | 预期差异 |
|---------|---------|
| 简单问题（"GIL 是什么？"） | 两者差别不大，Simple RAG 够用 |
| 比较类（"Python asyncio vs Rust async"） | Agentic RAG 会多轮检索，覆盖两个概念 |
| 跨领域（"LLM Agent 的 Planning 方法"） | Agentic RAG 会搜多篇文档综合 |
| 需要重写（"怎么做真正的并行？"） | Agentic RAG 可能换关键词搜到 multiprocessing |

观察维度：
- **检索轮次**：Agentic RAG 应该比 Simple RAG 多
- **命中文档数**：复杂问题上 Agentic RAG 应该覆盖更多文档
- **回答质量**：复杂问题上 Agentic RAG 应该更完整
- **耗时**：Agentic RAG 更慢（多轮 LLM 调用）

### 关键代码结构

```python
# Simple RAG：Python 控制检索，Agent 只负责回答
async def simple_rag(question):
    docs = retrieve(question, top_k=3)    # Python 代码做检索
    context = format(docs)
    return await Runner.run(agent, f"文档：{context}\n问题：{question}")

# Agentic RAG：Agent 控制一切
async def agentic_rag(question):
    agent = Agent(
        tools=[semantic_search, keyword_search, read_document, list_all_topics],
        instructions="你的检索策略：1.分析问题 2.检索 3.评估 4.不够就继续..."
    )
    return await Runner.run(agent, question)
```

两者的区别就在于**谁控制检索决策**：代码还是 Agent。

## 深入：RAG 的检索是怎么实现的

### 关键词匹配（练习代码用的方式）

看用户问题和文档有多少词重合：

```
用户问："Python GIL 是什么？"
文档 A："Python GIL 详解" → 匹配 "Python" + "GIL" → 高分 ✅
文档 B："Rust 所有权系统" → 没匹配 → 低分 ❌
```

致命问题：用户说"怎么做真正的并行？"，文档里写的是"multiprocessing"，关键词对不上就搜不到。

### 向量检索（生产环境的方式）

核心思想：**把文本变成数字向量，用向量距离衡量语义相似度。**

```
离线阶段（建索引）：
  文档库 → 切分成段落 → 每段过 embedding 模型 → 向量存入向量数据库

在线阶段（检索）：
  用户问题 → embedding 模型 → 查询向量
      ↓
  向量数据库：找 top-k 最近的文档向量
      ↓
  返回对应的原始文档段落
      ↓
  塞进 prompt → LLM 回答
```

语义相近的文本，向量距离就近。所以即使用户说"真正的并行"，文档写的是"multiprocessing"，因为语义相近也能匹配上。

### Embedding 模型

把文本变成向量的专用模型。和 LLM 架构基底相同（都是 Transformer），但训练目标不同：

```
LLM：           输入文本 → 预测下一个 token → 输出文本
Embedding 模型： 输入文本 → 压缩成一个向量 → 输出向量
```

| 模型 | 提供方 | 维度 | 特点 |
|------|--------|------|------|
| text-embedding-3-small | OpenAI | 1536 | 便宜、质量好、最常用 |
| text-embedding-3-large | OpenAI | 3072 | 质量更好、成本翻倍 |
| BGE-M3 | BAAI（智源） | 1024 | 开源、多语言、可本地部署 |
| GTE-Qwen2 | 阿里 | 多种 | 开源、中文效果好 |

Embedding 模型已经预训练好了，直接用就行。大多数场景不需要自己训练。如果领域非常专业（通用模型理解不好），可以用领域数据微调 embedding 模型，但这是优化手段，不是必须的。

注意和 LLM 内部 embedding 层的区别：LLM 的 embedding 层是给每个 token 分配向量（中间产物），RAG 的 embedding 模型是把整段文本压缩成一个向量（最终输出）。

### 文档切分策略

Embedding 模型有输入长度限制（通常 8k token），长文档必须切分。切分质量直接影响检索效果。

| 策略 | 做法 | 优缺点 |
|------|------|--------|
| 固定长度 | 每 500 字切一段 | 简单但会切断句子，上下文断裂 |
| 自然边界 | 按段落、标题、空行切 | 语义完整，但段落长度不一 |
| 滑动窗口 + 重叠 | 500 字一段，相邻段落重叠 100 字 | **最常用方案**，保留上下文 |
| 语义切分 | 计算相邻句子相似度，相似度骤降处切 | 效果最好，实现复杂 |

生产环境典型方案：**先按标题粗切，再对长段落用滑动窗口 + 重叠细切。** 每个 chunk 附带元数据（来源文件、章节、序号），方便追溯和拿相邻段落。

### 检索方式对比

| 方式 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 关键词匹配 | 词重合计数 | 简单、快、精确匹配强 | 同义词搜不到 |
| BM25 | 统计算法（TF-IDF 改进版） | 不需要 GPU、成熟稳定 | 基于词，语义理解弱 |
| 向量检索 | embedding + 余弦相似度 | 语义理解强，措辞不同也能搜到 | 精确匹配反而弱 |
| 混合检索 | BM25 + 向量检索，两路合并 | 兼顾精确和语义 | 实现复杂一点 |

生产环境一般用**混合检索**——BM25 抓精确匹配，向量检索抓语义相似，两路结果合并后重排序。

## 深入：Agentic RAG 的控制流

### 改进的层面不同

```
RAG 系统的分层：

┌─────────────────────────────────────┐
│  决策层：搜什么？搜几次？够不够？      │ ← Agentic RAG 改进这里
├─────────────────────────────────────┤
│  检索层：向量检索 / BM25 / 混合检索   │ ← 传统检索技术，两者都用
├─────────────────────────────────────┤
│  存储层：切分、embedding、向量数据库   │ ← 传统检索技术，两者都用
└─────────────────────────────────────┘
```

底层的检索引擎（向量数据库、embedding、切分）是一样的。区别在最上面的决策层：**Simple RAG 是代码写死的 if-else，Agentic RAG 是 LLM 实时推理。**

### Agent 的实际运行过程

每一轮就是一次 LLM 调用，prompt 不断累积。同一个 Agent 既负责"决定下一步做什么"，也负责"评估之前搜到的够不够"——没有单独的评估模块。

```
第 1 轮 LLM 输入：
  system: 你是研究助手，可用工具：search, read
  user: "对比 Python asyncio 和 Go goroutine"
→ LLM 输出：调用 search("Python asyncio")

第 2 轮 LLM 输入：
  （包含第 1 轮的决策和结果）
→ LLM 看到只有 Python 的信息，判断缺 Go 的
→ LLM 输出：调用 search("Go goroutine")

第 3 轮 LLM 输入：
  （包含前 2 轮的所有决策和结果）
→ LLM 看到两边都有了，判断信息够了
→ LLM 输出：生成最终回答
```

### 三层控制结构

```
开发者控制（硬边界）：提供哪些工具、每个工具连什么数据源、max_turns 上限
Instructions 引导（软建议）："优先语义搜索"、"比较类问题搜两个概念"
Agent 自主决策（运行时）：搜什么关键词、先用哪个工具、够不够、什么时候回答
```

### 检索失败时的处理

向量检索**永远会返回 top-k 个结果**，哪怕完全不相关（只是"距离最近的"）。Simple RAG 拿到垃圾结果也硬答。Agentic RAG 的应对：

- **换关键词重试**：search("真正的并行") 结果不好 → search("multiprocessing CPU 并行")
- **换工具**：语义搜索太模糊 → 改用关键词精确匹配
- **先浏览再定位**：list_topics() 看有什么 → 再针对性搜索
- **承认找不到**：搜了几轮都没有 → 回答"未找到相关信息"

工程上可以在工具内部加相似度阈值过滤，低于阈值返回"未找到"，给 Agent 一个明确的失败信号。

### RAG 的应用范围

RAG 的本质是**让 LLM 基于你指定的数据来工作**。问答是最典型的场景，但不止于此：

| 应用 | 数据源 | LLM 做什么 |
|------|--------|-----------|
| 知识库问答 | 内部文档 | 检索 → 回答问题 |
| 文档摘要 | 长报告 | 检索相关段落 → 生成摘要 |
| 辅助写作 | 公司过往案例 | 检索类似案例 → 帮写新方案 |
| 代码助手 | 项目源码 | 检索相关代码 → 解释/修改/生成 |
| 数据分析 | 业务数据报表 | 检索相关数据 → 做分析解读 |

共同点：LLM 自己不知道这些数据，通过检索塞给它，它再基于数据完成任务。
