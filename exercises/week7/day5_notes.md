## 一、状态管理：多轮对话怎么延续

### 问题

每次 `Runner.run()` 是独立的。第 1 轮问"介绍 LLM Agent"，第 2 轮问"你刚才说的 ReAct 是什么？"——如果第 2 轮看不到第 1 轮的对话，"你刚才说的"就无从谈起。

### 两种方案

| 方案 | 机制 | 历史存在哪里 | 限制 |
|------|------|-------------|------|
| `previous_response_id` | 服务端记住上一轮，客户端只传 ID | 服务端（OpenAI） | 需要 Responses API |
| `to_input_list()` | 把上一轮完整历史序列化为消息列表，下一轮作为输入 | 客户端（你的代码） | 对话越长 token 越多 |

Responses API 是 OpenAI 2025 年推出的新一代 API，服务端有状态，客户端只传 `previous_response_id` 即可延续对话。中转站不支持，所以用 `to_input_list()` 客户端方案：

```python
result1 = await Runner.run(agent, "介绍一下 LLM Agent")
input2 = result1.to_input_list() + [{"role": "user", "content": "ReAct 是什么？"}]
result2 = await Runner.run(agent, input2)
```

本质就是把对话历史塞回 prompt 的 messages 里。LLM 本身无状态，全靠你把历史传给它。

### 上限：context window

对话历史会不断膨胀，尤其 Agent 用了工具后历史里还包含工具调用和返回结果。当累积 token 超过模型的 context window（GPT-4o 128K，DeepSeek 64K-128K），就会报错或旧内容被截断。

### 超长上下文处理：三层策略

**第一层：减少输入——去掉工具调用的中间过程**

`to_input_list()` 返回的历史包含工具调用和返回结果，往往占 50%-80%。对后续对话来说只需要 Agent 的最终回答，中间过程可以去掉。

**第二层：摘要压缩——用 LLM 总结旧对话**

```
第 1-10 轮（8000 tokens）→ LLM 压缩 → 摘要（200 tokens）
第 11 轮输入 = 摘要 + 最近 2-3 轮完整历史 + 新问题
```

关键信息不丢，总 token 可控。代价是压缩本身要一次 LLM 调用。

**第三层：外部存储（RAG 做对话记忆）**

对话到几十轮以上，光压缩也不够。把历史存到向量数据库，按需检索取回：

```
每轮对话结束 → embedding → 存入向量库
新一轮对话 → 用户问题 embedding → 在向量库检索相关历史 → 只取回相关的几轮
```

本质就是 Day 3 学的 RAG 从"检索文档"换成"检索历史对话"，技术栈完全一样。

| 对话轮数 | 策略 | 场景 |
|---------|------|------|
| < 10 轮 | 直接传完整历史 | 短对话、客服 |
| 10-50 轮 | 去掉工具中间结果 + 摘要压缩 | 技术讨论、咨询 |
| 50+ 轮 | 外部记忆存储 + RAG 检索 | 长期助手、项目协作 |

### 三层记忆模型

| 层次 | 内容 | 存储位置 | 生命周期 |
|------|------|---------|---------|
| 短期记忆 | 当前对话窗口内的完整消息 | context window | 本次对话内 |
| 中期记忆 | 压缩后的对话摘要 | context window 中的一段摘要 | 本次对话内，可能被再次压缩 |
| 长期记忆 | 持久化的信息（用户偏好、历史决策） | 文件系统 / 向量数据库 | 永久，跨对话存在 |

边界判断：如果用户明天开新对话，哪些信息丢了会很痛？丢了无所谓的是短期/中期，丢了要重新说一遍的需要长期记忆。

### 长期记忆：触发与识别

不是每轮都存，有三种做法：

1. **规则匹配**：检测关键词（"记住"、"以后都"、"决定用"），零 token 成本
2. **LLM 判断**：对话结束时用小模型判断是否有值得保存的信息
3. **混合策略**（生产最常见）：规则预筛 + 小模型判断，大部分对话在规则层就跳过

好的长期记忆是**结论性的、可检索的、自包含的**——看到就知道是什么、为什么。

### 实际案例：Claude Code 的记忆机制

- 长期记忆：`.claude/projects/.../memory/` 目录下的 .md 文件，每条一个文件，全量加载到 context
- 短期记忆：当前对话的完整 context window
- 中期记忆：对话太长时系统自动压缩成 summary
- 没用向量库——记忆条数少（几十条），全量加载比 RAG 简单且可靠。条数涨到几千条才需要换向量库

### 向量数据库

向量数据库和 SQL 数据库是同一类东西（数据库软件），但解决不同的问题：

| 维度 | SQL 数据库 | 向量数据库 |
|------|-----------|-----------|
| 存什么 | 结构化数据（表格） | 向量 + 原文 |
| 查什么 | 精确条件（=、>、LIKE） | 语义相似度 |
| 返回逻辑 | 符合条件的所有记录 | 最相似的 top-k 条 |
| 代表产品 | MySQL、PostgreSQL | Chroma、Milvus、Pinecone |

向量库每条记录存两样：向量（用来算相似度的索引）和原文（找到后返回给 LLM 的文本）。查询时用近似最近邻（ANN）算法快速找到"最像的"，不需要暴力遍历。

## 二、成本优化：三个手段

### 手段 1：max_turns 限制

最直接的防护。一个 turn = 一次 LLM 调用 + 工具执行。

```python
# max_turns 是 Runner.run() 的参数，不是 RunConfig 的参数
result = await Runner.run(agent, task, run_config=run_config, max_turns=5)
```

实验对比：同一任务不同 max_turns 下效果不同。太小任务完不成，太大浪费 token。

### 手段 2：工具缓存

Agent 可能用相同参数重复调用工具。搜索类幂等工具（同 query 同结果）可以缓存：

```python
if query in _tool_cache:
    return f"[缓存命中] {_tool_cache[query]}"
```

缓存节省的不是 LLM token（调用还是发生了），而是工具执行成本（API 调用、数据库查询、网络请求）。

**实验结果**："LLM Agent" 被搜索 2 次，第 2 次命中缓存。

### 手段 3：模型路由

简单任务用小模型，复杂任务用大模型：

```
"什么是装饰器？" → 小模型（gpt-4o-mini / 7B）：便宜、快
"设计百万用户推荐系统" → 大模型（gpt-4o / 72B）：贵、质量好
```

路由器本身用小模型判断复杂度，成本可忽略。大部分请求是简单的，能省 50-80%。

**实验结果**：4 个任务路由判断全部正确（2 简单 + 2 复杂）。

## 三、质量评估：LLM-as-Judge

### 思路

用一个 LLM（Judge）评估另一个 LLM 的输出：

```
问题 + Agent 回答 → Judge Agent → 打分（准确性/完整性/条理性/总评）
```

### 实验结果

同一问题（"Python 有哪些并发方案？"），两个 Agent 回答：

| 维度 | 方案 A（简短） | 方案 B（详细） |
|------|--------------|--------------|
| 准确性 | 9/10 | 8/10 |
| 完整性 | 6/10 | 7/10 |
| 条理性 | 8/10 | 9/10 |
| 总评 | 7/10 | 8/10 |

详细回答总评更高，主要赢在完整性和条理性。简短回答准确性反而更高——因为说得少，出错的概率也小。

### LLM-as-Judge 的局限

- 本身是 LLM，可能有偏见（倾向给长回答高分）
- 不能替代专业领域的人工评估
- 但作为快速筛选工具很实用

### 生产环境的评估循环

```
Agent 回答 → 自动评估（LLM-as-Judge）
  → 低于阈值 → 人工审核
  → 高于阈值 → 直接放行
人工审核结果 → 校准自动评估标准 → 迭代改进
```

---

## 四、三个主题的关系

状态管理让 Agent 能做多轮对话，成本优化让它在预算内运行，质量评估让你知道它干得好不好。三者组合是把 Agent 从实验室搬到生产环境的基础设施。

## 五、代码要点

- `max_turns` 是 `Runner.run()` 的直接参数，不是 `RunConfig` 的字段
- `to_input_list()` 返回完整对话历史（包含工具调用），可直接作为下一轮输入
- `RunConfig` 中 `model_provider` 设置提供商，`use_responses=False` 使用 Chat Completions 模式
- 工具缓存是应用层实现（Python dict），不是 SDK 内置功能
